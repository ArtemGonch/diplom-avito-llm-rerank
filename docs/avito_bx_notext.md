# BX UsedCars NOTEXT 400k

## Приёмка и BX

Архив на Google Диске весит 3 794 834 688 байт. Название и сообщение
владельца указывают 400 тысяч выдач. Число выдач, период, сплиты,
история, атрибуты и эмбеддинги внутри файла пока не сверены.

1. После загрузки сверить размер и SHA-256, прочитать список файлов и
   README. Проверить типы, ключи, число строк и кандидатов по сплитам.
   Период и принадлежность к сплитам взять из источника.
2. Для базовой оценки читать сохранённый `baseline_score` и метки
   из полного пула каждого сплита. Сверить покрытие меток, знаменатели
   и опубликованные владельцем эталоны, если они приложены.
3. Если поставка содержит историю и снимки объявлений, проверить ссылки
   и `history_from <= event_at < search_at`. При моделировании брать
   только данные, доступные на момент выдачи. Параметры подбирать на
   части для разработки. Итог сравнивать попарно на фиксированном тесте.

```bash
python scripts/avito/evaluate_bx_baseline.py --archive "$BX_ZIP" --list-members
python scripts/avito/evaluate_bx_baseline.py --archive "$BX_ZIP" \
  --member-split train "$TRAIN_CANDIDATES_MEMBER" \
  --member-split test "$TEST_CANDIDATES_MEMBER"
```

Имена и обозначения сплитов в примере подставляются после сверки
с README поставки. Если файл содержит `split`, можно использовать
`--member` и сохранить метки источника. Временные файлы занимают
место в системном `TMPDIR`. Скрипт извлекает выбранные файлы потоково,
а SQLite собирает группы по всем выбранным шардам.

Загрузчик проверен на прежнем TEXT-пилоте. Все 31 784 кандидата,
1 000 выдач и десять метрик совпали с оригиналом. Первичная
`NDCG_b0.8(target_contact_s_d7)` равна 0,48385284659867683 на 18
пригодных группах. Это контроль воспроизведения прежнего результата.

## Embeddings CG внутри поставленного пула

Подготовлен скрипт для сравнения точного косинуса с BX на одном наборе
кандидатов. Один запуск обрабатывает один сплит из одного или нескольких
Parquet. Нужны `serp_x`, `source_row_index`, `baseline_score`, целевая
метка и `snapshot_id` либо подтверждённый статический `item_id`.
Строки одного запроса могут быть разбросаны между файлами.

В каждом из двух каталогов эмбеддингов требуются `keys.parquet`
и двумерный `vectors.npy` с одинаковым порядком строк. Ключ запросов —
`serp_x`, ключ объявлений задаётся `--item-key`. В метаданных обеих
таблиц ключей требуются `embedding_model`, `bx_split` и
`bx_candidate_sha256`. Для одного Parquet это SHA-256 файла. Для нескольких
это SHA-256 отсортированных в лексикографическом порядке шестнадцатеричных
SHA-256 файлов, разделённых символом новой строки без завершающего перевода
строки. Модель и размерность векторов должны совпадать. В приватном
манифесте запуска фиксируют SHA-256 файлов ключей и векторов, а по
манифесту генерации сверяют происхождение и доступность эмбеддингов
на момент поиска.

```bash
python scripts/avito/evaluate_bx_embedding_cg.py \
  --candidates "$TEST_CANDIDATES" --split test \
  --query-embeddings "$QUERY_VECTORS" --item-embeddings "$ITEM_VECTORS" \
  --label target_contact_s_d7 --k 5 10 20
```

- Recall@K — доля известных положительных кандидатов, попавших в первые
  K позиций. Кандидаты с неизвестной меткой занимают позицию. В среднее
  входят группы с хотя бы одной известной положительной меткой.
  Если K не меньше размера пула, Recall@K для такой группы равен 1.
- BX NDCG считается с тем же протоколом, что у базового скора.
  Сначала исключаются строки без метки, затем применяются веса
  `0.8 ** rank`, ранги с единицы, и `IDCG + 1e-5`. Однородные
  группы исключаются. При равных оценках используется `source_row_index`.
- Если в группе отсутствует эмбеддинг запроса или кандидата, группа
  сохраняет порядок BX. Отчёт показывает результат по всем группам и
  отдельно по группам с полным покрытием.

Эта оценка измеряет порядок только внутри поставленного пула. Для
оценки генерации по всему каталогу нужны временной срез каталога,
ключи положительных объявлений и подтверждённая доступность на момент
поиска. Прогон с настоящими эмбеддингами зависит от состава 400k.
