# LLM-профили предпочтений: литература и проверяемые варианты для Avito Auto

Дата проверки первичных источников: **29.10.2026**. Статус: исследовательский
дизайн; новые LLM-вызовы, обучение и ranking evaluation здесь не выполнялись.

## Что именно предстоит доказать

Сейчас доступны 100 пользователей, 79 с карточками и 9 010 анализируемых
user–item, типизированные поисковые фильтры. Новый набор не содержит полной
выдачи с экспозициями/кликами, коммуникаций, фотографий и описаний. Некоторые
атрибуты восстановлены поздними снимками; временная доступность не доказана.
Числа проверены по [агрегату User View](../results/current/metrics/avito_user_view.json),
ограничения — по [описанию данных](avito_user_view.md).

Зафиксированный 22 октября LLM-слой — редакторский отбор 515 canonical facts
двумя агентами для 100 профилей. Это не 100 вызовов Qwen и не измеренный рост
качества ранжирования. Он может выиграть в выборе полезного сочетания фактов,
но не добавляет недоступную семантику: семейность, надёжность или мотив покупки
нельзя получить как проверенные факты из марки, цены и кузова.

Ниже пересказаны методы, эксперименты и ограничения полных текстов. Абзацы
«Перенос» и последующие варианты — наши гипотезы, а не результаты авторов.

## Шесть первичных работ

### 1. Language-Based User Profiles for Recommendation — Dai, Zhou, Joachims, 2024

[Статья, arXiv:2402.15623v1](https://arxiv.org/html/2402.15623v1).
LFM использует LLM-encoder для сжатия истории названий фильмов и оценок в
текстовый профиль; другой LLM решает rating prediction, pairwise preference
и pairwise choice. Сравнения: прямой LLM по истории, NMF, средняя оценка.
Эксперимент — 300 пользователей MovieLens с ровно 150 оценками, случайные
подвыборки истории и исключённые из них тестовые фильмы; это не temporal SERP.
Оцениваются RMSE/MAE, ошибки парного выбора и разбираемость ответа.

Сила — явный контроль «профиль против той же истории». Сжатие обычно не портит
парные задачи, полезно при cold start. Ограничение: прямой LLM лучше при большой
истории в rating prediction; zero-shot LFM не использует дополнительную
межпользовательскую информацию так, как NMF. Перенос: сейчас сравнивать
компактность и полезность отбора; после получения временных labels — будущий
выбор. Автомобильные просмотры нельзя автоматически считать положительными
звёздочными оценками.

### 2. End-to-end Training for Recommendation with Language-based User Profiles — Gao et al., 2024, версия 2025

[Статья, arXiv:2410.18870v2](https://arxiv.org/html/2410.18870v2),
[официальный код LangPTune](https://github.com/ZhaolinGao/LangPTune).
Профиль генерируется offline; embedding decoder ранжирует товары скалярным
произведением. Обучение чередует contrastive learning декодера и RLSO
генератора по рекомендательной полезности. Нужны последовательности
взаимодействий, item metadata, отзывы и будущие targets.

На Amazon Movies&TV/Books используются четыре исторических товара и один
будущий, NDCG/MRR/Recall@20, zero-shot, отдельное обучение компонентов,
collaborative и no-profile controls; интерпретируемость проверяется людьми.
Сила — оптимизация профиля по downstream задаче и дешёвое применение после
генерации. Существенный отрицательный результат: в ablation Movies&TV
NoProfile-CL даёт NDCG@20 0.0543 против 0.0494 у профиля длиной 512 tokens:
языковое сжатие теряет информацию. Перенос: сейчас нельзя обучить такой метод
на 100 описательных профилях; после labels сравнивать профиль с несжатой
историей при одинаковом encoder/ranker, а не только с zero-shot LLM.

### 3. Transparent and Scrutable Recommendations Using Natural Language User Profiles — Ramos et al., 2024

[Статья, arXiv:2402.05810v2](https://arxiv.org/html/2402.05810v2).
UPR сначала извлекает аспекты из пользовательских отзывов и ранжирует их
детерминированно по оценкам, coverage и significance. Затем LLM получает
отзывы по top-аспектам и пишет профиль до 200 tokens; rating predictor
дообучается на профиле и товаре. Это уже гибрид эвристики и LLM.

Amazon Movies&TV и TripAdvisor: warm-start 8:1:1, RMSE/MAE, MAP/NDCG только
по оценённым test items, пять участников оценивают текст; редактирование
профиля проверяется искусственным добавлением предпочтений. Сила — проверка
управляемости и прозрачная предварительная селекция. Слабости — зависимость
от review text, перевес положительных отзывов, галлюцинации и потери при
сжатии; condensed ranking не равен реальной выдаче.
Перенос: сейчас полезен именно сильный эвристический selector. После появления
коммуникаций — извлечение аспектов из собственных слов пользователя; seller
description не является его мнением. Работа не доказывает преимущество
LLM-отбора над атрибутивными правилами.

### 4. Towards Explainable Temporal User Profiling with LLMs — Sabouri et al., 2025

[Статья, arXiv:2505.00886v1, UMAP Adjunct](https://arxiv.org/html/2505.00886v1).
GPT-4o-mini строит short-/long-term тексты из истории; SBERT кодирует их,
attention объединяет представления, MLP оценивает пару user–item. Нужны
timestamps, названия и достаточно длинные описания. На Amazon Movies&TV и
Video Games применяется chronological 60/20/20, Recall/NDCG; controls —
центроид тех же item embeddings, temporal fusion без LLM, popularity и MF.

Сила — отделение временного эффекта от генерации. Выигрыш менее устойчив на
коротких историях Games: дробление уменьшает поддержку; полноценного
исследования объяснений с пользователями нет. Перенос: сейчас можно проверить
устойчивость фактов по временным окнам, после временного контракта —
предсказательную пользу. Attention weight сам по себе не доказывает причинную
важность автомобильного атрибута.

### 5. When LLM-Inferred User Context Adds Value in Production Streaming Recommendation — Sabouri et al., 2026

[Препринт, arXiv:2609.38999v1](https://arxiv.org/html/2609.38999v1).
Четыре варианта пересекают centroid/LLM narrative и полную/short+long историю;
SBERT и обучаемый MLP общие. На 10 000 пользователей production streaming,
каталоге примерно 240 тысяч объектов и chronological 80/10/10 измеряются
full-catalog Recall/NDCG/HR, diversity, coverage и novelty.

Это важный отрицательный контроль: для всей популяции Narrative NDCG@10
ниже centroid на 26.9%, TemporalNarrative — на 15.2%; выигрыш обнаружен у
explorers, составляющих около 18%. Тексты уменьшают catalog coverage и novelty.
Сила — общие downstream компоненты и полный каталог. Ограничения — одна
платформа, один generation/encoding pipeline; explorer определяется по test
взаимодействиям post hoc, готового online gate нет. Перенос: после новых данных
нужны срезы и fallback, но нельзя выбирать «кому поможет LLM» по будущему
поведению. Сейчас допустима только гипотеза об неоднородности пользы.

### 6. GISTBench: Evaluating LLM User Understanding via Evidence-Based Interest Verification — Fostiropoulos et al., 2026

[Препринт, arXiv:2603.29112v2](https://arxiv.org/html/2603.29112v2).
LLM возвращает интересы со ссылками на evidence objects. Отдельный judge
проверяет смысловую релевантность доказательств; код считает engagement и
проверяет пороги. Interest Groundedness разделена на precision/recall,
Interest Specificity проверяет различимость интересов. Нужны тексты объектов
и типизированные положительные/отрицательные действия.

Используются синтетические когорты на основе реальных short-video историй,
публичные datasets и проверка на 593 реальных пользователях с опросами.
Выявлены ошибки подсчёта и приписывания действий; общая instruction-following
способность не гарантирует качества профиля. Сила — разделение правдивости,
покрытия и специфичности. Слабости — single-model judge, достаточные истории,
зависящий от набора моделей recall oracle; temporal drift не оценивается.
Перенос: сейчас числители и ссылки считать кодом, LLM оставить выбор смысла;
пороги short-video не переносить на Avito. После коммуникаций появится материал
для смысловой проверки, но groundedness всё равно не заменит NDCG.

## Три воспроизводимых варианта

**A. Проверка редакторской пользы сейчас.** Заморозить fact store/hash и
имеющийся LLM-отбор. Для каждого пользователя взять одинаковое число фактов
`k`, равное размеру его LLM-саммари; controls — priority top-k, priority с
разнообразием разделов и random-k с фиксированными seeds. Все видят те же
canonical facts. Сравнить покрытие explicit constraints, независимых аспектов,
повторяемость и длину. Провести слепую парную человеческую оценку полезности
для одной задачи — понять текущие ограничения и альтернативные сценарии.
Порядок вариантов балансировать, критерии зафиксировать до оценки. Парные
интервалы считать по пользователям. Это оценка выбора фактов, а не latent
preference recovery; автоматическое покрытие правил само по себе не докажет
пользу LLM. Одинаковое `k` не означает одинаковые tokens: длину отчитать отдельно.

**B. Память нескольких сценариев.** Следующий отдельный опыт: одинаковая
таблица evidence, максимум шесть fact IDs и два сценария; LLM только группирует
известные факты с abstain. Controls — текущие кузов×КПП×цена и детерминированная
группировка с теми же лимитами. До просмотра результатов разметить различимые
сценарии и конфликты с последним matched поиском. Проверять полноту, ошибочные
объединения и устойчивость при удалении одного объявления/дня; качество
сценариев оценивать слепо. Один offline вызов на профиль, фиксированные
model revision/prompt/temperature, до 4096 input и 384 output tokens; raw
evidence обрезается одинаково. Это новая гипотеза, не воспроизведение статей.

**C. Семантическое дополнение после данных Ромы.** При наличии rank-time,
as-of attrs, выдач и кликов зафиксировать один temporal split, candidate set
и ranker: attributes; attributes+raw-text/BM25/embedding; attributes+LLM-memory;
attributes+raw-history embedding. Все варианты получают одинаковые доступные
до показа тексты, одинаковый лимит истории; генерация использует бюджет B и
кэшируется. Сравнить NDCG@10, coverage, нарушения фильтров, стоимость генерации
и inference. Отдельно проверить короткую историю и смену фильтров. Профиль
считать полезным только при добавочной пользе против сильного text control;
gate выбирать на dev, не по test-срезам. Если доступны лишь коммуникационные
саммари, явно учитывать уже выполненное сжатие и его неизвестные потери.

Приоритет: A даёт честный ответ на задание 22 октября; B проверяет конкретную
семантическую способность сверх одиночного top-атрибута; C связывает её с
дипломным reranking claim после появления нужного протокола данных.
