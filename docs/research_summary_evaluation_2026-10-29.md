# Проверка пользы LLM-саммари: литература и протокол

Дата проверки источников: 29.10.2026. Это исследовательская постановка, не результат нового LLM-run или ранжирования. Основания проекта: [задание 22.10](task_2026-10-22_artem.md), [User View](avito_user_view.md), [проверенный агрегат](../results/current/metrics/avito_user_view.json).

Сейчас доступны 100 пользователей, 79 с карточками, типизированные поисковые фильтры; новых SERP с impressions/click labels, коммуникаций, текстов и фотографий объявлений нет. Существующий LLM-редактор выбрал **515 canonical facts**, не генерировал новые утверждения, не обучал Qwen. Поэтому возможное преимущество сейчас — полезность отбора при ограниченном объёме. Проверка известных fact IDs защищает формат и происхождение, но не доказывает корректность исходной эвристики или истинные желания пользователя.

## Что оцениваем

[Arustashvili, Balog, *A Survey on Natural Language User Profiles for Recommendation: Methods, Datasets, and Metrics*, EMNLP 2026](https://aclanthology.org/2026.emnlp-main.2207/) — обзорная рамка, отдельно от шести первичных исследований ниже. Проверены PDF, §5 и Table 3: RAET задаёт пару «оцениваемый выход — reference». Саммари относительно истории означает groundedness; рейтинг относительно будущих взаимодействий — downstream accuracy; соответствие реальным интересам требует самого пользователя. Тип оценщика — человек/LLM — отдельная ось. Scope обзора — связные пользовательские профили; перенос рамки на внутреннюю agent memory — наше методологическое решение. Обзор не даёт универсальной метрики и прямо исключает строгий межстатейный метаанализ из-за неоднородных протоколов.

## Шесть первичных работ

**1. Gao et al., *End-to-end Training for Recommendation with Language-based User Profiles* (LangPTune, preprint 2024; проверена v2, 12.02.2025).** [Статья](https://arxiv.org/html/2410.18870v2), [авторский код](https://github.com/ZhaolinGao/LangPTune). Из четырёх прошлых товаров с metadata/reviews строится профиль; RLSO оптимизирует генератор по ranking reward, contrastive learning — embedding recommender. Оценка: Amazon Books/Movie-TV, Recall/MRR/NDCG; отдельно люди и GPT-4 угадывают следующий фильм из двух фиксированных вариантов. Плюс — разделение оптимизации системы и человеческой полезности, ablations длины/обучения. Ограничение: человеческие 58.89% против 54.67% zero-shot **не значимы**, p=0.201; против raw history 57.11%, p=0.624. В Table 4 обученный raw-history control превосходит профиль: NDCG@20 0.0543 против 0.0494. Сейчас переносим задачу понимания; обучение требует других масштабов и labels.

**2. Wang et al., *LettinGo: Explore User Profile Generation for Recommendation System*, KDD 2025.** [Статья](https://arxiv.org/html/2506.18309v1), [официальный код](https://github.com/microsoft/DKI_LLM/blob/main/LettinGo/README.md). Несколько LLM исследуют варианты профиля долгой истории; downstream correctness создаёт пары для DPO. Вход — item attributes/sentiment, последние десять взаимодействий передаются рекомендателю отдельно. MovieLens-10M, Amazon Books, Yelp; последние items, Accuracy/F1 классификации, пользователи с более чем 70 взаимодействиями. Плюс — профиль выбирается по задаче, не красоте текста. Минус — результат не равен SERP NDCG, длинная rating history отличается от Avito implicit views. Важная воспроизводимость: README публикует **GRPO-версию**, DPO обещана; это не paper-exact code. Сейчас заимствуем controls, обучение откладываем до независимых labels.

**3. Peng et al., *MemRerank: Preference Memory for Personalized Product Reranking*, preprint 2026, v3 от 17.06.** [Статья](https://arxiv.org/html/2603.29247v3), [авторский dataset release](https://huggingface.co/datasets/zhiyuanpeng/amazon-c4-user-purchase-history). Query-independent within/cross-category memory из покупок до target; Qwen2.5-7B обучается GRPO по setwise reward и небольшому quality regularizer. Текущая v3 оценивает фиксированные top-100, четыре retrievers, две категории, MRR@10/5; 1-in-5 — операция обучения/сравнения, не весь benchmark. Macro MRR@10×100: 7.41→8.00 относительно сильнейшего baseline. Есть отрицательные срезы: BLAIR/Electronics 11.81→11.28, Beauty 5.63→4.11. Плюс — no-memory/raw-history/without-RL и held-out retriever; минус — синтетические review-derived queries, узкие категории. Проверенный release не содержит найденной ссылки на отдельный официальный training-code; обещание кода в статье не подтверждает доступность. Сейчас применима экспериментальная логика, после данных — ranking protocol.

**4. Min et al., *FActScore: Fine-grained Atomic Evaluation of Factual Precision in Long Form Text Generation*, EMNLP 2023.** [Статья](https://aclanthology.org/2023.emnlp-main.741/), [официальный код](https://github.com/shmsw25/FActScore). Генерация разбивается на атомарные утверждения; люди либо retrieval+LLM проверяют поддержку надёжным источником, исходный домен — биографии. Плюс — видны отдельные неподтверждённые сведения вместо одной общей оценки. Ограничение для Avito: factual precision не измеряет полноту, выбор важных фактов или рекомендационную полезность. Сейчас адаптируем ручной audit утверждение→источник; запуск Wikipedia verifier для приватных профилей методологически не подходит. После свободного текста потребуется также отдельная оценка omissions.

**5. Zheng et al., *Judging LLM-as-a-Judge with MT-Bench and Chatbot Arena*, NeurIPS 2023.** [Статья](https://arxiv.org/html/2306.05685v4), [официальные prompts/code](https://github.com/lm-sys/FastChat/tree/main/fastchat/llm_judge). Оценки ответов GPT-4 сопоставлены с экспертными и crowdsourced предпочтениями; исследованы position, verbosity, self-enhancement biases. Плюс — диагностические перестановки и human agreement; минус — согласие в чатах не валидирует оценку автомобильных интересов. Сейчас основной reference — независимая разметка человеком. Если добавлять LLM-judge, менять стороны A/B, скрывать методы, фиксировать judge revision и калибровать на людях; это вспомогательный сигнал, даже если модель-судья отличается от генератора.

**6. Schnabel et al., *Recommendations as Treatments: Debiasing Learning and Evaluation*, ICML 2016.** [Статья](https://proceedings.mlr.press/v48/schnabel16.html), [авторские code/data](https://www.cs.cornell.edu/~schnabts/mnar/). Рассматривает наблюдаемость feedback как selection mechanism; propensity weighting оценивает риск и обучает matrix factorization, эксперименты включают Coat и Yahoo ratings. Плюс — явные условия debiasing. Минус — нужны корректные ненулевые propensities/идентифицирующие предположения; временной split сам exposure bias не исправляет. Сейчас из списка просмотренного нельзя восстановить возможности выбора и вычислить unbiased lift. После SERP-логов это методологический ориентир; наличие позиций само по себе ещё не даёт propensities.

## Доступный эксперимент: наше предложение

1. **Заморозить** fact store, текущий editorial cache, hashes, правила и порядок. Для каждого пользователя задать K равным числу фактов в существующем LLM-обзоре; priority heuristic и section-diverse heuristic получают тот же K и те же canonical sentences. Совпадение числа фактов контролирует объём лишь приблизительно: дополнительно показать слова/символы и sensitivity при общем token budget. Старый cache с `model_revision=not_exposed` означает воспроизводимое воспроизведение выбора, не воспроизводимую регенерацию модели.
2. **Независимая слепая разметка.** Подготовить две пары на пользователя: LLM–priority и LLM–diverse, случайно переставить A/B. Таблица разметки оставляется пустой; mapping методов хранится отдельно. Два оценщика видят одинаковые источники без fact priorities и названий методов. До просмотра вариантов сформулировать reference-вопросы по источникам: актуальные явные ограничения, разные наблюдаемые сценарии, существенный конфликт/исключение, неизвестное. Оценивать поддержку, пропуск важного, смысловой повтор, риск неверного вывода и общую полезность; разрешить tie и insufficient evidence. Экспертная полезность не равна самоидентификации реального пользователя.
3. **Метрики:** paired win/tie/loss, точность ответов на reference-вопросы, время ответа, unsupported/overstated claims, omissions и redundancy. Единица анализа — пользователь: 200 пар не означают 200 независимых пользователей. Дать paired bootstrap CI по пользователям, agreement оценщиков и результаты отдельно для 79 с карточками/21 без них. Не награждать совпадение с собственными priorities или section coverage: это круговая оценка. Структурные показатели остаются diagnostics, окончательная выгода пока не измерена.
4. **Усилить без новых данных:** проверить одинаковые дубликаты, перестановки фактов, удаление одного события, маскирование priorities; новый pinned selector сравнивать с frozen отдельно. Семантическая гипотеза — LLM лучше сохраняет связность нескольких сценариев, обнаруживает смысловые повторы между разделами и выбирает полезную оговорку вместо ещё одного частотного факта. Число разделов этого не доказывает. Если нужного отношения нет среди canonical facts, текущий selector его создать не может; добавить atomic relation можно только отдельным проверенным этапом с evidence.
5. **Temporal diagnostic отдельно:** построить prefix-only факты/поиски до заранее выбранного cutoff и проверить согласованность с будущими действиями/фильтрами. Существующий full-history cache для этого непригоден: он видел suffix. Нужны новые prefix summaries, as-of snapshots; неопределённые/будущие attrs исключить и показать потерю покрытия. Совпадение с будущим событием — predictive diagnostic; отсутствие события не является negative label, выборочный contact не раскрывает intent. Без SERP candidates это **не NDCG качества выдачи**, не counterfactual эффект и не преимущество для пользователя.

После получения данных фиксировать query-time history/filter cutoff и candidate pool, сравнивать один downstream ranker с no-profile, raw history, rules, LLM memory; separately обучаемый и frozen encoder. Отчитывать retrieval recall, NDCG/MRR, clicks/contacts отдельно, стоимость, latency, slices и paired uncertainty. Communications/text/photos создают реальный простор для семантики — intent, negation, требования и их evidence — но их наличие и пользу ещё предстоит проверить.
